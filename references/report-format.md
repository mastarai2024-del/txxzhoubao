# 报告格式

## 周报类型与排版

| 周报类型 | 本期位置 | 上期参照 |
|---|---|---|
| 机器人产品周报 | 在对应飞书文档定位本人所在行和本期进展列 | 读本人上一期进展列，沿用模块标题、字段、顺序和列表 |
| Alpha 周报 | 在对应飞书文档定位本次日期章节的 Highlight 表，按「事项及报告人」找到本人相关专题，填写对应的「说明」栏 | 读上一期日期章节的 Highlight 表，优先看同专题，其次看同栏相近专题 |

以本期实际结构和用户手工调整为准。对照上期的标题原文、加粗、编号或项目符号、列表层级和缩进。写入飞书时用原生块还原。只改排版时保留已确认的内容和链接。Alpha 的共同汇报专题按本次授权填写本人部分，保留已有内容。

Alpha 周报出现以下专题时，可参照同类上期的写法。

- App 专题先写版本进展，沿用「本版重点」等小标题并用原生编号逐项简述新增功能，末尾写已确认的下版本号。提审、过审和正式发布分别核实。应用商店过审按报告时区只写日期，如“6 月 12 日通过 App Store 审核”。
- 数据上传专题分条写已确认的方案及结论，取数或上传范围可放在方案下面作为子项。
- 远程控制专题简述方案，再写已完成的评审次数和预计上线版本。

## 无既有格式的独立草稿

没有可用格式时采用以下字段，顺序保持一致。

| 字段 | 写法 |
|---|---|
| 模块标题 | 加粗，用项目或方向命名，大事项单独成块 |
| 事项 | 一句话说明本期在做什么 |
| 目标 | 已确认的本期目标与交付物，期限有依据再写 |
| 进展 | 通常3–5条，每条约30字；用动词开头，只写有证据的结论和动作 |
| 风险 | 仅在直接影响交付时保留一行，写明实际阻塞和影响，涉及版本冲突时注明所在系统 |
| 下周计划 | 通常2–3条，回应本期进展；建议须明确标注，日期不能补造 |

已确认的跨团队资源需求并入进展或计划。条数服从证据，不凑数。月报最后一项按现有格式改为下月计划。模块用既有分隔方式，默认 Markdown 分隔线；写入飞书时采用工具支持的原生结构。

表达示例均为虚构写法，不可当作本期素材：

- “明确升级失败重试规则，补齐需求验收条件。”是文档成果，不改写成“升级功能上线”。
- “核对支付异常，当前仍待研发处理。”保留状态，不改写成“解决支付异常”。
- 会议只写有本人关联的结论；“参加需求会”本身不足以说明工作进展。

交付前核对同类上期的标题和列表、上期计划回应、本人关联、本期日期及完成状态。写入后还要检查条目所在单元格、编号和缩进在飞书网页上的实际显示。来源明细和读取缺口放在草稿外的说明中，保留给用户核对。
